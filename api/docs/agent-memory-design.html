Agent 长期记忆架构方案

01 / The Story

一条信息如何进入三层记忆并在未来被复用

每轮输入先作为不可变原始事件保存，并立即服务当前任务；达到窗口或任务边界时，Consolidate Once 对新增事件只理解一次，并行形成证据索引、短期任务存档和长期候选。

01 / 事件

保存原始输入

用户消息、文件和工具结果进入同租户事件流，保留来源、时间和证据引用。

02 / 当前

工作记忆立即生效

当前请求进入工作记忆，更新任务状态、对话窗口、即时指令和执行结果。

03 / 收束

一次理解并行分流

Consolidate Once 对新增窗口执行剪枝、切块和抽取，并行输出证据、任务存档和长期候选。

04 / 治理

候选形成长期主记录

长期候选经过价值、重复、冲突、敏感和作用域检查后，执行 CREATE、REFINE、CORRECT 或 SUPERSEDE。

05 / 复用

恢复、检索与生命周期治理

同一任务通过短期记忆恢复，新任务通过长期记忆复用；gc 负责降权、合并、归档和明确删除。

主线：原始事件是证据来源；工作记忆服务当前步骤；短期记忆保证任务连续；长期记忆只保存经过治理的跨任务稳定信息。

02 / Three Layers

三层记忆

01 / 当前

工作记忆

承载当前步骤正在使用的信息。任务执行和回答都发生在这里。

  • 组成：当前任务状态、对话窗口、工具与文件结果、用户即时指令、已排除方向
  • 时长：秒到分钟
  • 退出：任务结束立即清空
02 / 任务

短期记忆

保存当前任务仍需持续使用的信息。需要时检索并加载回工作区，使长任务能够连续执行；任务结束后按规则清理。

  • 组成：任务检查点、恢复摘要、中间状态、未完成问题
  • 使用：按需检索并加载回工作区
  • 退出：任务结束后按规则清理
03 / 长期

长期记忆

保存经过证据绑定和价值治理、跨任务仍需复用的稳定信息；原始事件和用户输入摘要属于独立的证据与来源层，不作为长期主记录本身。

  • 类型：稳定事实、用户偏好、长期约束、关键决策、项目进展
  • 时长：长期保留，持续更新
  • 退出：归档或按用户要求删除
结构级展开：以下内容严格对应总览图中的结构节点。工作记忆的五个节点是一个运行时对象的五个子对象；短期记忆的四个节点是一份任务检查点的四个组成部分；长期记忆的五个节点是共享同一主记录外壳的五种语义类型。
实现边界：公共身份、安全、证据、版本和使用统计作为外层 Envelope 统一处理；各结构节点只展开自身负责的业务数据。三层可以引用同一原始事件，但短期记忆不会转换或二次压缩为长期记忆。
字段采用 English field_name（代码与数据库字段）+ 中文业务含义 的双语形式；JSON 中仍保留标准英文键，避免破坏接口格式。

强制身份上下文

tenant_id 是所有路径的安全边界；由服务端认证上下文产生，调用方不可覆盖。其余字段用于租户内部的业务定位。

tenant_id · REQUIRED · SERVER-SOURCED租户编号 · 必填 · 服务端生成user_id用户编号session_id会话编号task_id任务编号agent_idAgent 编号trace_id调用追踪编号

租户隔离不变量：任何数据路径都不能脱离 tenant_id

MemoryService.write / read / gc、META、工作记忆、短期记忆、长期记忆、精确键、向量索引、图谱关系、缓存、后台重建任务和审计事件，全部从同一份只读 TenantContext 获取 tenant_id。META 只负责租户内部的 user / project / agent 作用域，不能替代租户隔离。

1. 服务端解析从已验证的 JWT、mTLS 或服务账号解析 tenant_id，不信任请求正文和 query 参数。
2. 只读注入中间件生成不可变 TenantContext，并注入 write、read、gc 和后台任务。
3. 全路径过滤主键、唯一键、查询、恢复、删除、重建和派生索引都以 tenant_id 为第一过滤条件。
4. 失败即拒绝缺失或不匹配时 fail closed；外部不暴露目标是否存在，内部记录拒绝审计。

工作记忆 · 当前请求的运行对象

对应总览图中的五个节点。它们不是五张独立表，而是同一个 WorkingMemory 对象在运行期间持续更新的五个子对象。

执行单位Request / Workspace
主要载体模型上下文、Redis、运行时对象
退出条件请求完成、任务关闭或窗口收束
1. 接收请求用户输入、工具回调或子 Agent 结果进入工作区。
2. 装载上下文建立任务锚点，激活近期消息和相关记忆。
3. 执行当前步调用模型、工具或子 Agent，更新运行状态。
4. 更新五个子对象任务、窗口、工具、即时指令和排除方向分别更新。
5. 继续或收束预算充足则继续；达到边界则冻结增量窗口。

对话窗口

保存当前模型调用真正需要看到的上下文引用，并负责控制窗口预算和增量收束位置。

更新时机：工具开始、返回、超时、重试或生成新产物。

用户即时指令

已排除方向

记录已经验证不适用的实现路径及其原因，防止 Agent 在同一任务中反复回到错误方向。

短期记忆 · 当前任务的连续性记录

对应总览图中的四个节点。它们共同构成一份 TaskCheckpoint 或当前任务快照，用于窗口切换、暂停和恢复。

执行单位Task / Checkpoint
主要载体任务快照、检查点表、缓存
退出条件任务完成、TTL 到期或主动归档
1. 触发存档步骤完成、暂停、切换或窗口接近上限。
2. 读取增量只处理上次游标之后的新事件和当前工作状态。
3. 生成检查点形成任务检查点、恢复摘要、中间状态和未完成问题。
4. 更新快照检查点追加，当前快照按字段覆盖更新。
5. 唤回或释放按 tenant_id + task_id 恢复；任务结束后按策略清理。
任务检查点恢复摘要中间状态未完成问题
字段归属原则：检查点负责定位“保存到了哪里”；恢复摘要负责快速重新进入任务；中间状态保存当前仍有用的过程结果；未完成问题明确继续执行所缺少的输入和阻塞项。

长期记忆 · 跨任务复用的稳定主记录

对应总览图中的五种语义类型。它们不是一条记录中的五个必填分区，而是共享同一个 Canonical Memory Envelope 的五类长期记录。

LTM-FACT

稳定事实

记录经过证据支持、未来任务仍需要知道的客观事实。

LTM-PREF

用户偏好

记录用户在表达、交互和结果形式上的稳定选择，并注明适用条件和强度。

{
  "preference_dimension": "方案说明顺序",

  "conditions": [

}

LTM-RULE

长期约束

记录跨任务持续生效、不能被普通步骤随意覆盖的规则和边界。

{

  "applies_to": [

  ],
  "exception": null
}
执行作用：在写入和治理阶段作为硬约束校验，不只是提示文本。
LTM-DEC

关键决策

记录已选择的方案、被放弃的备选项、决策原因和后续影响。

Product Story：同一段对话如何演进成一组 JSON 对象

这一版不再逐个解释字段，而是展示系统在每个时刻真正持有什么对象。沿着同一个 event_id 往下看，可以看到原始事件如何进入工作记忆、并行形成短期任务快照和长期素材，最后在未来任务中产生行为变化。

DIALOGUE → JSON STATE → PRODUCT EFFECT
USER · 原始对话 “以后给我讲技术方案时，先讲总体架构，再展开字段和代码。当前先把 Agent 记忆方案的三层字段梳理清楚，今天形成一版可执行方案。”
AGENT · 即时效果 “收到。本轮先完成完整的总体结构；‘先讲架构，再讲字段和代码’立即作用于当前回答，并在后台作为长期偏好候选独立治理。”
阅读方式： 每一步只看“对象发生了什么变化”。同一份短期快照不会再压缩成长时记忆；长期候选始终从原始事件窗口独立提取。

租户身份边界 · 全链路强制约束

tenant_id 不是普通业务字段，而是 MemoryService 的安全上下文。它必须来自服务端认证结果，并成为 API、三层记录、派生索引、后台任务和审计事件的共同分区键。

TENANT BOUNDARY

运行逻辑：服务端派生、只读注入、全路径过滤、失败关闭

客户端可以提交 user_id、task_id、project_id 等业务标识，但不能决定 tenant_id。任何内部函数在缺少 TenantContext 时都不得访问存储。

01 认证验证 JWT、mTLS 或服务账号，解析 tenant_id、principal_id 和权限声明。
02 注入构造只读 TenantContext；请求体中的 tenant_id 被忽略或在不匹配时拒绝。
03 执行write/read/gc、META、resume 与 rebuild 只能接收服务端 TenantContext。
04 过滤所有 SQL、KV、向量和图谱查询都显式绑定 tenant_id，不允许跨租户 fallback。
05 拒绝审计缺失或不匹配时不读取、不覆盖、不删除；记录最小拒绝审计。
不可覆盖来源

tenant_id 只从已验证的 auth/session/service identity 派生，业务参数和 LLM 输出均无权修改。

复合键规则

任何可冲突标识都与 tenant_id 组成主键或唯一键；相同 user_id、task_id、project_id、normalized_key 可安全存在于不同租户。

拒绝语义

缺失返回 TENANT_CONTEXT_REQUIRED；显式覆盖不匹配返回 TENANT_CONTEXT_MISMATCH；跨租户资源对外统一表现为 NOT_FOUND，内部记 TENANT_BOUNDARY_REJECTED。

03 / Service Layer

MemoryService 统一编排六个动作

上层 Agent 只面向三个 API：write（写入）、read（检索）和 gc（生命周期处理）。三个入口在业务参数之前都必须绑定服务端生成的只读 TenantContext，再映射为六个内部动作；没有 tenant_id 的调用一律拒绝。

架构总览

所有路线先绑定服务端 TenantContext：tenant_id 不从业务请求读取，也不能被 Agent 或 LLM 覆盖。write、read、gc、META、短期恢复、长期回读、索引清理和后台重建都以 tenant_id 为第一过滤条件；之后才执行六个内部动作和四档内容检索。

展示完整的记忆写入、检索和生命周期清理关系。

主写入链：外部输入先进入工作区，工作区再调用 MemoryService.write，完成一次窗口沉淀并形成任务存档
任务存档：一次沉淀直接形成任务存档，同时生成长期素材和证据索引，不从短期摘要二次生成长期记忆
检索复用：MemoryService.read 可先用 META 返回用户画像、权限和作用域约束，再选择任务存档、Express 精确定位、向量索引或知识图谱，最后回读有效主记录并组装 Context Package
GC 生命周期：MemoryService.gc 负责短期过期、长期归档或删除以及派生索引清理
01 / 写入

工作区提交写入（write）

外部输入先进入工作区，再由工作区调用 MemoryService.write 提交事件或待收束窗口。

触发：新消息提交、工具结果产生或窗口需要收束
02 / 暂存

任务存档进入短期

Consolidate Once 一次理解后生成任务存档，保存任务检查点、恢复摘要、中间状态和未完成问题。

触发：空间不足、步骤结束或任务切换
03 / 唤回

短期记忆唤回（read）

MemoryService.read 检索同一任务的任务存档，组装 Context Package 后返回工作区。

触发：任务恢复或需要回看
04 / 调用

为任务或子 Agent 调用长期记忆（read）

MemoryService.read 根据任务目标、子 Agent 角色、当前步骤和用户请求构造查询。复杂查询由 LLM 生成检索计划并拆分子查询；代码再按作用域、索引、有效状态和权限检索长期记忆，必要时沿证据索引回查原始对话或文件证据，最终组装 Context Package。

触发：新任务、子 Agent 启动、知识缺口、关系补全或上下文不足
05 / 沉淀

长期候选治理与主记录写入

Consolidate Once 已完成消息剪枝、对话切块、证据绑定和长期候选抽取。05 沉淀只接收长期候选，执行价值、显式性、敏感、作用域、重复、冲突和时效检查，再通过 CREATE、REFINE、CORRECT、MERGE 或 SUPERSEDE 写入长期主记录。

触发：10 条消息、空闲 10 分钟、上下文 70%、会话结束或明确记住
06 / 释放

生命周期释放（gc）

由 MemoryService.gc 编排释放动作，处理短期过期、长期归档或删除，并同步清理向量、图谱和缓存等派生索引。

触发：TTL 到期、定时治理或用户删除
剪枝与切块边界：消息剪枝只从本次长期记忆总结的输入中排除重复、无效和低价值噪声，不删除原始事件；对话切块按任务、主题、时间和语义边界拆分，每个 chunk 必须保留 message_ids、evidence_ids 和时间范围。切块之后才生成长期候选，避免把整段对话压成一条过大的记忆。

MemoryService：对外只暴露三个入口

上层 Agent 只面向 write、read、gc 三个入口，不直接调用六个内部动作。对应关系固定为：write 管理 01 写入、02 暂存、05 沉淀；read 管理 03 唤回、04 调用；gc 管理 06 释放。

MemoryService.write(tenantContext, event)

负责写入链路

  • 租户前置：tenantContext 由认证中间件注入且只读；请求体中的 tenant_id 不能覆盖服务端值，缺失或不匹配时拒绝。
  • 01 写入：所有事件、窗口、WM / STM / LTM 记录都写入当前 tenant_id 分区。
  • Consolidate Once：窗口达到触发条件时只理解一次，并行生成任务存档、长期素材和证据索引。
  • 02 / 05 分流：Consolidate Once 已并行生成任务存档、证据索引和长期候选；02 将任务存档写入短期记忆，05 只治理长期候选并写入长期主记录。
MemoryService.read(tenantContext, query)

负责检索链路

  • Tenant + META 前置：tenant_id 先作为不可绕过的安全过滤；META 只在该租户内部返回用户画像、Agent 权限、user / project / agent 作用域和系统元信息。
  • 03 唤回：使用 tenant_id + task_id 检索任务存档；禁止仅按 task_id 恢复。
  • 04 调用：为当前任务或子 Agent 补充必要上下文，也用于处理跨任务知识缺口和关系补全。
  • 查询理解：已知 memory_id、memory_key 或明确槽位时走 Express 精确定位；普通语义问题走 Quick；复杂 query 可由 LLM 输出子查询、记忆类型、实体、关系、时间范围和是否需要证据回查。
  • 检索执行：每个 SQL、KV、向量和图谱查询都先绑定 tenant_id，再在 META 给出的租户内作用域和权限约束下定位 memory_id，并用 tenant_id + memory_id 回读主记录。
  • 返回结果：META 返回控制上下文；内容检索结果经去重、排序和权限过滤后组装为 Context Package 返回工作区，不把全部底层记录原样注入 Agent。
MemoryService.gc(tenantContext, policy)

负责治理链路

  • 06 释放：由 gc 在当前 tenant_id 分区内处理短期记忆 TTL 到期和任务存档过期。
  • 长期生命周期：归档低频内容，删除用户要求删除的记录，并处理失效版本。
  • 派生清理：按 tenant_id + memory_id 同步清理向量索引、图谱关系和缓存，并保留带 tenant_id 的审计记录。

租户隔离执行契约：tenant_id 是第一身份键，不是可选过滤器

MemoryService 的安全边界必须在数据访问层生效，而不能只依赖 META、Prompt 或上层 Agent。每次 write、read、resume、gc、delete 和 index rebuild 都使用同一份服务端 TenantContext；业务代码只能在当前租户内部继续按 user、project、agent 和 scope 缩小范围。

事件触发

05 / LLM Boundary

LLM 在六个动作中的参与边界

六个动作并非都必须调用 LLM：02 暂存和 05 沉淀是主要使用位置；03 唤回和 04 调用按复杂度选择；01 写入和 06 释放必须由确定性代码主导。

01 / 写入 · WRITE

原始记录不依赖 LLM

怎么用：代码先原样保存用户输入、工具结果和来源 ID。LLM 只可选做主题、敏感性和高价值事件标签；标签是建议，不能改变原文或阻断写入。

02 / 暂存 · CHECKPOINT

生成可恢复的任务存档

怎么用：Consolidate Once 时输入当前窗口、任务目标和已有状态，输出 task_state、resume_context、open_questions 和已排除方向；代码校验后写入短期记忆。

03 / 唤回 · RESUME

压缩同一任务的恢复上下文

怎么用：系统先按 tenant_id + task_id 确定性找到任务存档；内容过长时再让 LLM 按当前步骤压缩和排序，最终由代码组装 Context Package。

04 / 调用 · RETRIEVE

先形成检索计划，再由代码执行检索

怎么用：输入任务目标、子 Agent 角色、当前步骤、用户请求和可用作用域。系统先用确定性规则判断复杂度；复杂时由 LLM 输出 retrieval_plan，包括 sub_queries、memory_types、scopes、entities、relations、time_range 和 need_evidence。LLM 只决定“需要查什么”，不直接选择最终记忆记录；代码负责权限过滤、索引检索、有效性校验、去重排序和预算控制。只有 need_evidence=true 或候选存在冲突时，才沿 evidence_id 回查原始对话、文件或工具证据。

05 / 沉淀 · PROMOTE

剪枝、切块并生成长期候选

怎么用：输入新增窗口和证据索引。代码先保护必须保留的用户明确事实、决策和来源记录；LLM 可辅助标记重复回显、无效工具噪声和话题边界，生成 chunks。每个 chunk 再输出候选结论、记忆类型、适用范围、置信度、实体关系、evidence_ids 及 CREATE / REFINE / SUPERSEDE 建议；剪枝结果、证据存在性、状态、版本和最终落库均由代码校验与裁决。

06 / 释放 · GC

模型只能提出治理建议

怎么用：LLM 可辅助识别重复、可合并内容和低价值候选，但 TTL、引用计数、用户删除、合规到期、归档及级联清理必须由 MemoryService.gc(ctx, ...) 确定性执行。

六个动作统一采用同一套调用契约

LLM 输出始终是“候选解释或结构化建议”，不能直接修改记忆状态。

  • ① 路由：MemoryService 先确定当前是写入、暂存、唤回、调用、沉淀还是释放。
  • ② 最小输入：只提供当前动作需要的窗口范围、任务目标、候选证据、作用域和允许输出字段。
  • ③ 结构化输出：返回 JSON，包含候选结论、置信度、证据索引、不确定项和建议动作。
  • ④ 确定性校验：执行 schema、权限、证据存在性、重复、冲突、版本和状态检查。
  • ⑤ 执行与降级：校验通过后由代码写入或检索；模型失败时退回规则、原始存档或普通检索，不阻断主任务。
  • ⑥ 审计：记录 model_id、prompt_version、输入输出哈希、耗时、错误和重试次数。
主要使用 LLM 02 暂存生成任务恢复摘要；05 沉淀辅助消息剪枝、对话切块、长期候选生成、适用范围判断、证据绑定和实体关系抽取。
按复杂度选择 03 唤回仅在任务存档过长或需要按当前步骤重排时调用 LLM；04 调用面向普通任务和子 Agent 上下文组装。META、Express 和 Quick 不调用生成式 LLM；Normal 按需生成子查询与检索计划；Deep 通常调用 LLM 规划实体关系探索。LLM 不直接挑选最终记录，01 写入和 06 释放也只能把模型作为非阻断建议器。
必须保持确定性 原文保存、task_id 匹配、权限过滤、状态机、版本递增、TTL、引用计数、用户删除、合规清理和审计日志。
最终边界：LLM 负责理解、压缩、抽取和解释；MemoryService 负责路由、校验、状态迁移和执行。任何影响权限、版本、长期有效性和删除结果的动作，都不能由模型单独决定。

06 / Long-term Storage

一份主记录，两类查询索引

长期记忆只保存一次。向量和知识图谱不是两份独立记忆，而是同一条主记录的两类内容查询索引。META 是独立的控制面查询，只返回用户画像、权限和作用域；Express、Quick、Normal、Deep 则在这套存储结构上组合精确定位、向量召回、综合过滤和图谱关系探索。

长期记忆内部结构

一条长期记忆由一个主记录统一管理，再生成来源记录、向量索引和知识图谱结构。主记录、来源、向量和图谱都使用同一个 tenant_id + memory_id + 版本号。形成顺序是：Consolidate Once 完成消息剪枝、对话切块、候选抽取与证据绑定；05 沉淀再完成价值判断、去重合并、冲突处理、作用域与时效检查，最后写入主记录。

不是“一段消息固定生成一个向量记录和一个图谱记录”。 不是按单条消息机械生成记忆。系统先对新增消息窗口做剪枝，再按任务、主题和语义边界切成一个或多个 chunk；每个 chunk 可能不形成长期记忆，也可能生成一条或多条长期候选。候选通过治理成为长期主记录后，系统按照索引生成规则分别判断是否生成向量索引、知识图谱关系，或两者都不生成。
例 1：“我喜欢简洁、结构清晰的表达”形成偏好主记录，通常生成向量，不必进入图谱。
例 2：“模块 A 依赖模块 B”形成关系主记录，通常进入图谱，未必需要内容向量。
例 3：“项目采用 Neo4j 保存模块依赖”既可按语义检索，也有明确实体关系，因此可以同时生成向量和图谱投影。
普通寒暄或临时进度：可能只保留原始事件或任务存档，不进入长期主记录，也不建立两类索引。

“一份主记录、两类查询索引”描述的是内容记忆的存储逻辑。META 位于控制面，查询用户画像、权限、Agent 角色和 user / project / agent 作用域；Express、Quick、Normal、Deep 位于内容检索面。Express 使用主记录自身的唯一键或 KV 映射做精确定位，不形成第三类内容索引；Quick 和 Normal 主要使用向量索引，Deep 重点使用知识图谱。

一条记忆什么时候变成向量，什么时候进入图谱？

先保存主记录，再按照索引生成规则做两个独立判断。向量和图谱不是二选一：一个负责按意思找，一个负责按关系找；只有确实需要时才生成对应索引。这里是写入阶段的索引生成规则，不是 read() 中的检索路由。

判断 A · 向量条件

未来是否可能用不同说法查找它？

只要内容本身有完整含义，并且后续需要按语义相似度召回，就生成向量。

  • 用户偏好、经验、总结和解决方法
  • 对话原话与未来问题可能不是同一措辞
  • 内容经过压缩后仍能独立表达一个意思
判断 B · 图谱条件

是否存在稳定、可验证的实体关系？

能够提取“谁 / 什么—什么关系—谁 / 什么”，并且关系对后续查询有价值，才进入知识图谱。

  • 项目、模块、人员、决策和规则可以明确识别
  • 依赖、负责、采用、影响、替代等关系稳定
  • 关系有证据、适用范围和时间，置信度达到门槛

例：模块 A 依赖模块 B；张三负责项目 X。

工作区窗口如何一次沉淀为多路产物

MemoryService.write(tenantContext, event) 触发窗口收束后，只处理当前 tenant_id 下、上次位置之后的新对话，并只做一次 Consolidate Once。任务存档、长期素材和证据索引都继承同一 tenant_id。

01 冻结工作区窗口 截取本轮消息、工具结果和文件摘要，记录窗口起止消息编号。
02 Consolidate Once 只让 LLM 或抽取器理解一次窗口，避免短期和长期各自重复压缩。
03 形成三类沉淀产物 并行形成任务恢复信息、长期素材以及指向原始事件的证据索引。
04 写任务存档 取 task_state、resume_context、open_questions，形成任务检查点。
05 取长期素材 取 facts、preferences、constraints、decisions、progress，以及用于图谱投影的 entities 和 relations。
06 价值和冲突校验 去重、检查冲突、判断置信度；价值不足只保留短期或证据。
07 保存主记录和投影 长期记忆写主记录、证据、版本，并异步建立向量和图谱投影。
最终结果：同一个工作区窗口经过一次 Consolidate Once，形成“一个任务存档 + 一组长期素材 + 一组证据索引”。只有通过价值校验的候选才成为长期主记录；查询时先用索引找 memory_id，再回主记录获取完整内容。

07 / Retrieval

先取 META，再选择四档内容检索

MemoryService.read(...) 首先绑定服务端 TenantContext，再在当前租户内部执行 META 和四档内容检索。META 只负责 user / project / agent 作用域，不能替代 tenant_id 安全过滤；所有精确键、向量、图谱和主记录回读都必须显式带 tenant_id。

CONTROL / META

元信息检索

在服务端 TenantContext 已绑定的前提下，只返回当前租户内的用户画像、权限、Agent 角色和 user / project / agent 作用域；不召回长期记忆正文。

  • 调用形式：read(tenantContext, mode="META", user_id, agent_id, project_id)
  • 查询入口：tenant_id 分区内的画像、配置、权限和作用域 KV
  • 返回 retrieval_scope、allowed_memory_types 与稳定偏好
  • 不进入向量索引、知识图谱和证据回查
LLM：不调用 · 控制面查询，可单独供 Agent 使用
L1 / EXPRESS

快速定位

目标记忆的键已经明确时，通过 MemoryService 的元数据定位能力找到对应 memory_id；它不是对主记录正文做数据库全文查表。

  • 查询入口：memory_id、memory_key、type + topic 或明确槽位
  • 底层唯一键或 KV 映射必须使用 tenant_id + memory_key 定位 memory_id
  • 先校验 tenant_id，再校验 META 作用域、权限、状态和版本，并以 tenant_id + memory_id 回读主记录
  • 不做内容模糊匹配，不进入向量和知识图谱
LLM：不调用 · 仅适用于已知目标键或引用
L2 / QUICK

快速检索

以向量索引为主要入口，适合普通历史回忆、偏好和相似内容查询。

  • 查询入口：向量索引
  • 向量召回 memory_id，关键词可作为辅助
  • 回读主记录并去重、排序
  • 不拆问题、不生成总结
LLM：不调用 · 平衡速度与召回率
L3 / NORMAL

标准检索

结合当前对话理解问题，适合大多数需要历史信息的 Agent 任务。

  • 查询入口：向量索引为主，主记录负责条件过滤
  • 必要时由 LLM 改写问题并拆分子查询
  • 多路向量召回后按作用域、类型、时间和有效状态筛选
  • 存在明确关系条件时补充一跳图谱；需要核验时回查证据
  • 按需由 LLM 压缩为子 Agent 可用摘要
LLM：按需调用 · 默认综合模式
L4 / DEEP

深度检索

在标准检索基础上增加图谱关系探索，适合原因、影响和多跳问题。

  • 查询入口：向量索引定位起点，知识图谱负责多跳展开
  • LLM 拆分问题并识别实体、关系、作用域和时间约束
  • 代码执行图谱遍历，并回读关系链对应的有效主记录
  • 必要时回查原始证据，LLM 再汇总内容与关系
LLM：通常调用 · 失败时降级为标准检索

08 / Forgetting

记忆生命周期治理

MemoryService.gc(tenantContext, policy) 只治理当前 tenant_id 下的记录：先降权、合并和归档，只有用户要求或合规到期才最终删除；删除和索引清理不能跨越租户边界。

触发一

长期未使用

根据最近实际使用时间、使用次数、确认情况和保护状态，降低默认检索权重；长期未使用不代表内容错误。

days_since(last_used_at) ≥ unused_days
AND use_count ≤ low_use_threshold
AND protected = false
动作：DOWNRANK → ARCHIVE_CANDIDATE；默认不执行 DELETE。
触发二

容量超过上限

先由租户容量聚合对象判断是否越过高水位，再从允许淘汰的记录中选择低价值、高占用候选。

触发三

内容重复或过时

精确重复使用内容指纹，语义重复使用稳定键和语义指纹；过时内容通过有效期、复核时间和新版本关系判断。

OR similarity ≥ merge_threshold

动作：MERGE、REFINE 或 SUPERSEDE；旧记录退出 active，但保留版本和证据链。
触发四

明确删除要求

用户删除、租户管理员请求或保留期到期会形成独立删除请求；先退出检索，再执行同租户级联物理清理。

(USER_REQUEST OR now ≥ retention_until)
AND legal_hold = false
AND tenant_id matches TenantContext
动作：PENDING_DELETE → TOMBSTONED → PURGED；外部统一返回 NOT_FOUND，内部保留最小拒绝与删除审计。

触发字段不应全部堆进长期内容主记录

为了避免高频检索、容量统计和删除任务不断改写内容版本，生命周期数据拆成五个物理对象：long_term_memory、memory_usage_stats 和 memory_lifecycle_state 通过 tenant_id + memory_id 关联；memory_deletion_request 使用 tenant_id + deletion_request_id 并保存目标 memory_id；tenant_memory_quota 使用 tenant_id + quota_scope + scope_id 聚合。MemoryService.gc 按当前租户统一读取。

防止误删的四条规则

pinned=true、protected=true、reference_count>0 或 legal_hold=true 的记录不得自动删除；没有完整证据链的记录只能降权或待审；gc 必须持有 TenantContext，跨租户目标对外按 NOT_FOUND 处理并写拒绝审计；删除采用 pending_delete → tombstoned → purged 三阶段，任何阶段失败都不能影响其他租户。

当前生命周期治理的实现基础
  • 已有时间和访问次数驱动的记忆活跃度计算，支持定时检查低活跃记忆。
  • 容量超限由 tenant_memory_quota 的高水位触发；候选必须经过 eviction_eligible、pinned、protected、reference_count 和 legal_hold 门禁。
  • 重复与过时治理同时使用 normalized_key、content_hash、semantic_fingerprint、valid_to、review_at 和版本关系，合并后保留证据链。
  • 本方案把这些能力统一纳入 MemoryService.gc(tenantContext, policy)，内部再调用“释放”动作；所有降权、合并、归档和最终删除都限制在当前 tenant_id。

09 / Delivery

按三步完成落地

先把 tenant_id 作为不可绕过的安全上下文打进 MemoryService.write/read/gc，再补充检索、治理和质量评估；多租户隔离必须先于功能完整性验收。

先固化 TenantContext

从认证中间件生成不可覆盖的 tenant_id，把复合主键、索引分区、查询过滤、拒绝语义和审计写入 write/read/gc 的公共底座。

打通三层记忆与检索

完成 WM / STM / LTM、META、短期恢复、主记录、向量和图谱，并确保所有路径以 tenant_id 为第一过滤条件。

上线治理与隔离回归

加入冲突处理、归档删除、索引重建、失败重试和双租户回归夹具，把拒绝审计纳入发布门禁。

租户隔离 Validation Harness

构造两个租户共享完全相同的业务标识，专门验证“同名不串数据”。测试不能只验证正常返回，还要验证覆盖、删除、恢复和索引重建均无法越界，并保留拒绝审计。

const tenantA = fixture({ tenant_id: "tenant_A", user_id: "user_001", task_id: "task_001", project_id: "project_001", normalized_key: "preference:report_style" }); const tenantB = fixture({ tenant_id: "tenant_B", user_id: "user_001", task_id: "task_001", project_id: "project_001", normalized_key: "preference:report_style" });
路径测试动作必须通过的断言
writeA、B 分别写入相同 user_id / task_id / normalized_key，但内容不同。形成两组 tenant-scoped 主记录和索引；不能覆盖另一租户，复合唯一键分别成立。
META / read分别以 A、B 的 TenantContext 执行 META、Express、Quick、Normal、Deep。每条候选、memory_id 和 Context Package 只来自当前 tenant_id；跨租户目标对外返回 NOT_FOUND。
resumeA、B 使用相同 task_id 保存多个 checkpoint，再分别恢复。查询条件必须包含 tenant_id + task_id；A 永远不能恢复 B 的快照，反之亦然。
gc / delete在 A 中删除与 B 同名的 memory_key、task_id 或 normalized_key。只清理 A 的主记录、证据、缓存、向量和图谱；B 的数据与索引数量保持不变。
index rebuild分别重建 A 和 B 的精确键、向量与图谱投影，并模拟失败重试。重建作业固定单一 tenant_id，不扫描或写入另一租户；缺失 tenant_id 的 job 必须拒绝。
拒绝审计构造 tenant_id 缺失、请求覆盖不匹配和跨租户资源 ID。记录 operation、principal、可信 tenant_id、目标哈希、reject_reason 和 trace_id；审计中不包含另一租户正文。
验收问题 通过标准
信息是否进入了正确层级？ 普通过程不进入长期记忆；长期记忆必须经过价值判断。
记忆为什么被保存或调用？ 每条记忆都能说明来源、范围、状态和本次命中原因。
一个索引故障是否影响主记录？ 主记录正常保存，索引可以重试和重建。
租户隔离是否覆盖全部路径？ 两个租户使用相同 user_id、task_id、project_id 和 normalized_key 时，write、META/read、resume、gc 和索引重建均不能返回、覆盖或删除另一租户的数据。
删除是否完整？ 只清理当前 tenant_id 下的主记录、向量索引、图谱和缓存，并保留不泄露正文的最小审计凭证。
最终形成一个可控的记忆循环

新信息先在可信 tenant_id 边界内服务当前任务，有价值的结论再进入同租户长期记忆；需要时准确取回，过期后逐步退出，并且任何读取、恢复、删除和重建都可审计且不会跨租户。
