- 17 张数据库表，全部带 `tenant_id` 主键前缀

- Alembic 迁移管理
- Docker Compose 一键启动基础设施

**2. 租户隔离（100%）**
- `TenantContext` 不可变设计（`@dataclass(frozen=True)` + `__init__` factory-token 保护）
- 禁止业务代码创建 TenantContext，只能由 TenantResolver 创建
- `DevelopmentTenantResolver` 从 HTTP Header 解析（开发模式）
- `TenantContextMiddleware` 仅对 `/v1/memory/*` 路径生效，fail-closed
- 所有数据库查询必须带 `tenant_id`，Repository 基类强制校验
- 跨租户访问返回 `NOT_FOUND`，不泄露目标是否存在

**3. Write 链路（90%）**
- `POST /v1/memory/write` 统一入口，通过 `type` 字段区分三种命令：
  - `type: "event"` — 原始事件写入
  - `type: "consolidate"` — 手动触发 Consolidate Once
  - `type: "promote_candidates"` — 候选提升（排队 Outbox Job）
- 原始事件写入流程：
  1. 幂等去重（`idempotency_key` + `event_id` 双重检查）
  2. Working Memory 初始化（PostgreSQL + Redis 双写）
  3. ConsolidationPolicy 评估（消息数/Token/空闲/显式信号）
  4. 触发 Consolidate Once → 产出 Evidence + TaskCheckpoint + LongTermCandidate
- Consolidate Once 核心保证：
  - 事件窗口冻结（从游标位置到最新事件）
  - 并行产出三兄弟结果（Evidence / TaskCheckpoint / LongTermCandidate）
  - 三兄弟全部成功保存后才推进游标
  - 任一失败不回滚已保存数据，游标不推进
  - 游标使用 `SELECT ... FOR UPDATE` + 乐观锁版本号
  - 验证：候选必须来自原始事件、证据引用必须在窗口内
- `DeterministicConsolidator` 规则引擎：
  - user 消息 → FACT 候选（confidence=0.7）
  - assistant 消息 → FACT 候选（confidence=0.6）
  - 触发词"先讲总体架构，再展开字段和代码" → PREFERENCE 候选（confidence=1.0）

**4. Read 链路（85%）**
- `POST /v1/memory/read` 统一入口
- `RetrievalRouter` 自动模式路由（基于关键词和参数）：
  - `memory_id`/`memory_key`/`normalized_key` → EXPRESS
  - 有 `task_id` 无 `query` → RESUME
  - 含"为什么/原因/影响/依赖" → DEEP
  - 含"结合/同时/并且"或多 scope → NORMAL
  - 其他 → QUICK
  - 显式指定 `mode` → 直接使用
- 检索召回策略：
  - EXPRESS：精确键查找（memory_key → exact_key_store）
  - RESUME：读取最新 TaskCheckpoint
  - QUICK：仅向量检索
  - NORMAL：向量 + 精确键（如有 normalized_key）
  - DEEP：向量 + 精确键 + 图谱遍历（max_depth=3）
- `MetaPolicy` 构建租户内部权限控制：
  - allowed_scopes = [user:principal_id, workspace:workspace_id, agent:agent_id]
  - allowed_memory_types = 请求指定 or 全部五种
- 召回后处理：
  - 回读 `long_term_memory` 主记录（验证 active + scope + type + time_range）
  - 加权排序（语义相关性 35% + 置信度 15% + 重要性 15% + 显式度 10% + 新鲜度 10% + 使用权重 5% + scope 匹配 10%）
  - Token 预算控制（`estimate_tokens = ceil(len(content)/4)`）
  - Context Package 按 5 种 MemoryType 分组输出
  - 记录 `recalled_at` 和 `used_at` 使用统计
- `LLMRetrievalPlanProvider`：LLM 生成检索计划 + Pydantic Schema 校验 + 确定性 fallback
- `DeterministicRetrievalPlanProvider`：基于分隔符拆分子查询

**5. Candidate Governance（80%）**
- `CandidateGovernanceService` 完整实现 7 种治理动作：
  - `CREATE` — 新建长期主记录 + 版本 v1 + 排队索引投射
  - `REFINE` — 追加内容 + 版本递增 + 合并证据链
  - `CORRECT` — 纠正现有主记录
  - `MERGE` — 合并重复候选到同一主记录
  - `SUPERSEDE` — 退役旧记录 + 创建新记录 + 建立取代关系
  - `DEFER` — 暂不处理（置信度不足/冲突待解决）
  - `IGNORE` — 永久忽略（敏感内容/过期/无效 scope）
- 质量门禁（`_quality_gate`）：
  - 证据有效性 → `evidence_valid`
  - Scope 合法性 → `scope_valid`
  - 敏感度过滤 → `blocked_sensitivities`
  - 置信度阈值 → `minimum_confidence`（默认 0.6）
  - 显式度阈值 → `minimum_explicitness`（默认 0.5）
  - 陈旧度阈值 → `maximum_staleness`（默认 0.95）
  - 未来价值阈值 → `minimum_future_value`（默认 0.5）
- 去重检测（`_checks`）：
  - `exact_duplicate_id` — 精确键匹配（同 `normalized_key` + `scope` + `memory_type`）
  - `semantic_duplicate_ids` — 语义指纹匹配
  - `conflict_ids` — 内容哈希冲突（同 key 不同内容）
- 版本审计：每次状态变更记录到 `long_term_memory_versions` 表
- 索引投射排队（`_queue_projections`）：
  - EXACT — 始终创建
  - VECTOR — PREFERENCE 类型或有 semantic_fingerprint
  - GRAPH — type_payload 包含结构化 relations
  - CACHE — 始终创建

## 五、架构亮点

### 5.1 六边形架构（Ports & Adapters）

```
main.py → api/ → service/ → ports/ ← infrastructure/
                                    ↑
                              domain/ (纯数据)
```

- `domain/` — 零外部依赖，纯 Pydantic 模型
- `ports/` — 16 个抽象协议，定义契约
- `service/` — 核心业务逻辑，只依赖 ports 和 domain
- `infrastructure/` — 具体适配器，实现 ports
- 依赖反转：services 不直接依赖 infrastructure

### 5.2 多租户安全设计

- `TenantContext` 不可变（`frozen=True` + `__init__` factory-token 保护）
- 禁止业务代码创建或修改 TenantContext
- 所有数据库操作必须显式传入 TenantContext
- 17 张表全部以 `tenant_id` 作为主键第一列
- 跨租户访问 fail-closed，统一返回 `NOT_FOUND`
- 审计日志只记录目标哈希，不泄露其他租户正文

### 5.3 Consolidate Once 设计

- 事件窗口冻结（从游标到最新事件）
- 三兄弟并行产出（Evidence + TaskCheckpoint + LongTermCandidate）
- 原子游标推进（SELECT FOR UPDATE + 乐观锁版本号）
- 任一失败不回滚已保存数据
- 幂等重试保证
- 验证规则：候选必须来自原始事件、证据引用必须在窗口内

### 5.4 候选治理状态机

```
候选产出(pending) → 质量门禁 → 去重检测 → 治理动作
                                            ├── CREATE  → active 主记录
                                            ├── REFINE  → 版本递增
                                            ├── MERGE   → 合并到已有记录
                                            ├── SUPERSEDE → 退役旧记录 + 新建
                                            ├── DEFER   → 暂不处理
                                            └── IGNORE  → 永久忽略
```

### 5.5 检索路由与排序

- 7 种检索模式：AUTO / META / RESUME / EXPRESS / QUICK / NORMAL / DEEP
- 关键词自动路由（"为什么"→DEEP，"并且"→NORMAL）
- 多维度加权排序（7 个权重因子，全部可配置）
- Token 预算控制（按字符数/4 估算，超出截断）
- 回读校验：索引只返回 memory_id，最终结果必须回读 active 主记录
